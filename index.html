用途

软件方案、架构配置与实现调试使用同一份 Tile/Event 描述。分析对象包括总周期，关键资源利用率，也包括事件为什么等待、计算与搬运如何重叠、存储何时分配和释放。

使用者分析与决策
软件工程师在实现前或优化过程中预演软件流水。分析 Tile 划分、预取深度、发射顺序和多 lane 排布，检查搬运能否被计算掩盖、空泡在等待哪个输入，以及 stage 与片上存储是否足够。修改方案后对比周期、等待和物理占用，减少进入 CA/RTL 仿真前的试错成本。
硬件工程师将设计预期转为 CA/RTL 可逐事件对照的性能基线。核对实际启动、完成、依赖和资源并发是否符合预期，追踪额外仲裁、反压或同步等待。将偏差区分为软硬件实现问题、原始效率假设问题或模型遗漏，再通过新波形检查修正效果。
架构师快速搭建新架构的理论模型，探索资源空间并辅助定义架构 SPEC。配置 CP、MEM 和数据通路，评估计算吞吐、搬运带宽、读取延迟及片上容量的变化，判断新增资源是否改善关键路径。结合目标算子所需的吞吐、带宽、容量和时延条件，为 SPEC 中的资源配置与性能目标提供依据。既可固定软件方案分析硬件收益，也可重新调整 Tile、stage 与调度，探索软硬件联合优化方案。

参数变化，流水哪里受影响？

01 · Softmax 效率减半：0.5 → 0.25

总周期 +20.2% · 13,940 → 16,756 clk

Softmax 输出变晚，TC 等待输入的 bubble 变长、增多，流水完成时间随之推迟，softmax瓶颈将严重影响tensor core的计算效率。

02 · KV stage 减半：6 → 3

总周期不变 · 13,940 clk

TMA_IN 新增槽位等待，TC 时序保持不变；当前模型与负载下，3 个 KV stage 已能维持原有性能，可以看出对本CASE，Shared mem空间冗余。

AI 工作流

项目提供三个性能分析 Skill。事件模型与结构化输出记录软件排布、资源约束和等待关系，供 AI 建模、比较方案及对照实现。

工作流输入与输出
1. Kernel → Events读取 kernel 和硬件配置，抽象主要计算、搬运、依赖及物理存储生命周期，生成 events.json（模拟器的输入）。
2. 事件排布优化在计算语义、工作量和访存约束下生成与检查候选排布，对比周期、空泡、资源利用率和存储占用。
3. 推演与波形对照将模拟器输出作为 AI 性能调优（自动分析 kernel 与波形）的中间层。把 kernel 中的主要动作与真实执行阶段映射到同一组事件，对照理论时序、数据就绪条件与实际等待，分析执行是否符合预期。

第三个 Skill：通过事件与依赖理解流水掩盖

summary.json / trace.json 提供事件的启动、吞吐窗口结束、完成时刻，以及空泡原因、等待的 Tile、对应生产者和存储生命周期。AI 可以沿这些关系检查：预取是否及时，数据就绪前是否还有计算可覆盖等待，以及实际波形中新增的空泡出现在什么位置。

理论基线Kernel → Tile/Event 模型 → TESS 理论时序与依赖
实际执行Kernel → FSDB / Verdi → 执行阶段提取与事件映射
对照分析两路结果 → AI 对齐事件、检查流水掩盖、归因执行偏差

模拟器边界及与 CA/RTL 的区别

TESS 描述设计人员在给定架构、软件排布和效率假设下的理论执行过程。它用于提出并检查性能预期；CA/RTL 用于观察更接近实际实现的执行行为，两者在优化与调试中相互对照。

维度TESS 理论推演CA / RTL 仿真
主要目标建立设计的性能预期，分析优化方向，并推动软硬件实现接近经检查的预期。CA 模型以尽可能贴近 RTL 的执行行为为目标；RTL 仿真用于检查具体实现的逻辑和时序表现。
描述内容Tile/Event、依赖、吞吐、延迟、资源共享与存储生命周期，由配置和软件排布显式描述。依据具体模型或 RTL 表达实现机制，例如发射、仲裁、反压与同步等细节。
如何使用结果在实现前比较方案，在实现后作为波形对照基线，检查偏差来源。观察实际执行过程，验证设计，并定位实现中的功能或性能问题。

CA 以贴近 RTL 为目标；TESS 提供设计人员的理论性能预期，推动 RTL 实现尽可能接近这一预期。这一预期需要有合理的参数与假设支撑，也可由RTL实际实现情况调整预期。

与公开工作的区别

TESS 与这些工具的共同点是都能支持架构分析，但目标和使用阶段不同：Timeloop 侧重映射空间搜索，Accel-Sim 侧重从指令执行行为得到接近硬件的结果；TESS 侧重把设计人员选定的 Tile/Event 静态排布推演成可检查的理论时序。

公开工作输入、目标与典型输出TESS 的侧重点与边界
Timeloop ↗输入：加速器层次结构、存储层级、数据流和映射约束。
目标：在较大的 mapping 空间中搜索并评估 DNN 工作负载的性能、数据移动和能效。
输出：不同映射方案的聚合代价，帮助比较架构和映射选择。		两者都可以用于架构探索，但 TESS 从一个明确的 Tile 划分和事件排布开始，继续展开到每个搬运、计算、依赖等待和存储槽生命周期的时间关系。它回答的是“这套排布为什么形成这些周期和 bubble、哪一类资源限制了它”，不负责替代 Timeloop 的大范围映射搜索。
Accel-Sim ↗输入：可执行 CUDA kernel 产生的指令 trace，以及 GPU 微架构和执行参数。
目标：重现指令级、warp 级和微架构资源的执行行为，并通过硬件结果校准模拟精度。
输出：接近实际 GPU 执行的周期、吞吐和性能计数器，用于性能预测与验证。		TESS 的输入是设计阶段可编辑的架构资源和 Tile/Event 静态调度，不需要先有完整的可执行 kernel，也不模拟指令发射、缓存命中、warp 分歧或动态仲裁。它先给出理论基线，再把理论事件与 CA/RTL 或 FSDB 中的执行阶段对齐，帮助定位预取、依赖和流水掩盖是否按设计发生；真实硬件行为仍需由 CA/RTL 和波形验证。

核心区别：TESS 的结果不是“尽可能准确地复现现有硬件”，而是把架构师和软件工程师的静态调度设想转成一份可复现、可解释、可与实现逐事件对照的性能预期，用于指导架构 SPEC、软件优化以及后续 CA/RTL 调试。
